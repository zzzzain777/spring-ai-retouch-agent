1. 这个模块解决什么问题

主项目是一个修图 Agent：用户说一句话，模型给出工具调用提议，Java 校验后执行。但模型不知道「京东服饰类目的首图必须白底、不许加促销文字」这类平台规范。把规范贴进提示词有三个问题：规范一多提示词就爆、模型可能视而不见、出了问题无法追溯是哪条规范。

这个模块的做法是：把规范做成可检索的知识库，把检索到的条款变成对「计划」的硬校验。

  • 检索不到规范 → 不通过，交人工核对；
  • 计划违反召回到的条款 → 不通过，列出条款、原因与出处；
  • 计划满足 → 放行。

它不是聊天问答式的 RAG。检索结果进的是校验器，不交给模型改写，没有生成（Generation）那一步。面试时别主动叫它 RAG，不然会被追问「你的 G 在哪」。准确说法是「向量检索 + 规则硬校验」，或者「用检索给校验器供给约束」。

另外它是独立接口（POST /api/compliance/check），没有接进主对话流程。这是刻意的：不动 Planner 和 AgentService，现有的 82 个测试和行为评测结果都不受影响。代价是目前得由调用方主动调它。

3. 一次请求的完整流转

以这个请求为例：

POST /api/compliance/check        （需登录，SecurityConfig 里 anyRequest().authenticated()）
{
  "platform": "jd",
  "category": "apparel",
  "goal": "把这张商品图做成京东服饰类目的首图",
  "tools": ["flip_layer"]
}
  1. ComplianceController 收请求，@Valid 校验四个字段非空（goal 还限长 500）。
  2. ComplianceChecker.check() 先调 indexService.ensureIndexed()：首次调用才把规范灌进向量库，之后直接返回。
  3. 拼检索词：query() 把 goal 和工具的中文名拼起来 —— flip_layer 查 ToolRegistry 得到「翻转」，最终得到
    把这张商品图做成京东服饰类目的首图；计划操作：翻转
  4. 检索：searchForCompliance() 先按 platform == 'jd' and category == 'apparel' 过滤元数据，再做向量 Top-5、阈值 0.3。本例召回 5 条：rule-7、rule-3、rule-1、rule-2、rule-8。
  5. 空召回就结束：召回为空直接返回「没有检索到适用规范，需人工核对」，不放行。
  6. 判规则：对召回到的每条条款，逐条规则看关键词是否出现在条款原文里（String.contains）。命中后检查计划工具：require-any 要求计划含其中之一，forbid 要求计划不含。
  7. 汇总返回：passed、检索词、召回出处、逐条 findings（带相似度）、violations。

本例结果：不通过。rule-1（背景必须纯白，0.724）缺 remove_background；rule-2（需裁剪或补边到规定比例，0.722）缺 crop_canvas。rule-3（禁止文字）命中但满足，因为计划里没有 set_layer_text。

一句话记住整条链路：目标 + 工具 → 拼成检索词 → 元数据过滤 + 向量召回 → 规则表逐条判 → 通过 / 列出违规条款。

4.1 KnowledgeDocumentLoader —— 把 Markdown 切成带元数据的片段

职责：读 classpath:knowledge/*.md，解析开头的 front-matter，按 ## 把正文切成一条条条款。

String[] parts = body.split("(?m)^##\\s+");
for (int i = 1; i < parts.length; i++) {
    String part = parts[i];
    int nl = part.indexOf('\n');
    String heading = (nl >= 0 ? part.substring(0, nl) : part).trim();   // 「rule-1 背景」
    String text    = (nl >= 0 ? part.substring(nl + 1) : "").trim();     // 条款正文
    if (text.isEmpty()) continue;

    String ruleId = heading.split("\\s+")[0];                            // 「rule-1」
    Map<String, Object> m = new LinkedHashMap<>();
    m.put("docId", docId);        m.put("docVersion", version);
    m.put("platform", platform);  m.put("category", category);
    m.put("ruleId", ruleId);      m.put("sourceRef", docId + "#" + ruleId);
    out.add(new Document(heading + "\n" + text, m));
}

为什么按 ## 切，而不是按字数切

通用 RAG 常按固定字数切块（比如 500 字一块，重叠 50 字），因为文档结构不可控。这里的规范是结构化的，一条条款就是一个语义单元，按标题切有三个好处：不会把「背景必须纯白」和「尺寸 800x800」切进同一块导致检索含混；每块天然对应一个可引用的编号；sourceRef（如 JD-APPAREL-001#rule-1）能直接给人看。

不这么做会怎样：按字数切，命中后你只能说「大概在第 3 块」，没法告诉业务方违反的是哪一条；而且一块里混着多条规则，关键词匹配会误触发。

元数据是过滤的基础

platform 和 category 进了 metadata，检索时才能先把范围缩到「京东 / 服饰」。这叫元数据过滤（pre-filter），比先全库检索再筛选更准也更省。

4.2 KnowledgeIndexService —— 入库与幂等

职责：把片段写进向量库；同一份规范内容没变就不重复写。

String hash = sha256(chunks.stream().map(Document::getText).collect(joining("\n")));
String oldHash = jdbc.query("select content_hash from knowledge_doc where doc_id = ?",
        rs -> rs.next() ? rs.getString(1) : null, docId);

if (hash.equals(oldHash)) {            // 内容没变 → 跳过，省一次 embedding 的钱
    log.info("规范 {} 未变化，跳过入库（{} 块）", docId, chunks.size());
    continue;
}
vectorStore.delete(new FilterExpressionBuilder().eq("docId", docId).build());  // 先删旧向量
vectorStore.add(chunks);                                                       // 再写新向量
jdbc.update("insert into knowledge_doc(...) values (...) on conflict (doc_id) do update set ...");

为什么要判重

每次调用嵌入接口都要花钱、也要时间。应用每重启一次就把 24 条重新 embed 一遍，既慢又浪费。哈希比对让「内容没变就一次接口都不调」。

为什么先删后写：向量库没有「按 docId 覆盖」的语义。如果只 add，改过的规范会和旧版本同时存在，检索可能召回已经作废的条款。先按元数据 docId 删干净，再整份写入。

懒加载

private volatile boolean indexed;

public synchronized void ensureIndexed() {
    if (indexed) return;
    try { indexAll(); indexed = true; }
    catch (Exception e) { log.error("规范入库失败", e); }
}

ensureIndexed() 在第一次合规检查时才真正入库，而不是应用一启动就跑。原因：跑 @SpringBootTest 时没有嵌入密钥，启动即入库会让一大批与本模块无关的测试全挂。synchronized + volatile 保证并发第一次请求时只入库一次。

代价：第一次调 /api/compliance/check 要等 24 条 embedding，明显慢。这点写在边界里了。

4.3 KnowledgeRetriever —— 两档检索参数

职责：元数据过滤 + 向量 Top-K。对外是两个方法，差别只有参数。

/** 规范问答：按问题召回最相关的几条条款，不相关就返回空。 */
public List<Document> search(String platform, String category, String query) {
    return search(platform, category, query, topK, threshold);              // 3 / 0.5
}

/** 合规检查：按本轮目标召回适用条款，阈值更低、条数更多。 */
public List<Document> searchForCompliance(String platform, String category, String query) {
    return search(platform, category, query, complianceTopK, complianceThreshold);  // 5 / 0.3
}

private List<Document> search(String platform, String category, String query, int k, double minScore) {
    SearchRequest request = SearchRequest.builder()
            .query(query).topK(k).similarityThreshold(minScore)
            .filterExpression(scope(platform, category))   // platform == ? and category == ?
            .build();
    return vectorStore.similaritySearch(request);
}

为什么两档参数不一样

规范问答合规检查
问题形态一个明确的问题一个宽泛的目标
答错的代价答非所问，用户立刻看出来漏召回 = 漏检，没人看得出来
取舍宁可不答（Top-3 / 0.5）宁可多召几条再逐条判（Top-5 / 0.3）

这是整个模块里最值得讲的一个设计判断：同一个检索能力，因为下游用途不同，参数就该不同。问答的错误是「答错」，用户会纠正；合规的错误是「该拦没拦」，静悄悄地放过去。所以合规这边把阈值放低、条数放多。

4.4 ComplianceRuleProperties —— 规则表

@ConfigurationProperties("retouch.knowledge.compliance")
public record ComplianceRuleProperties(List<Rule> rules) {
    public record Rule(String id, String message, List<String> keywords,
                       List<String> requireAny, List<String> forbid) {
        public boolean matches(String text) {
            return keywords != null && keywords.stream().anyMatch(text::contains);
        }
    }
}

职责：把「条款里出现什么词」映射成「计划必须包含 / 禁止包含哪些工具」。规则写在 application.yml，新增检查项不用改 Java、不用重新编译。

为什么用关键词，而不是让模型判断条款是否被违反

三个理由，面试可以直接答：确定性（同样的输入永远同样的结果，可测试、可复现）、零成本（不调模型）、可审计（违规时能说清是哪条规则、缺哪个工具）。让模型判断的话，同一个计划两次调用可能给不同结论，这在「硬校验」里是不能接受的。

代价也要承认：关键词是脆的。条款换个说法（「白底」写成「背景色值 #FFFFFF」）就匹配不上。这属于已知边界，写在第 7 节。

4.5 ComplianceChecker —— 核心

拼检索词

String query(String goal, List<String> toolNames) {
    Set<String> labels = toolNames.stream()
            .map(name -> registry.find(name).map(ToolSpec::label).orElse(name))
            .collect(toCollection(LinkedHashSet::new));
    String goalText = goal == null ? "" : goal.strip();
    if (labels.isEmpty()) return goalText;
    return (goalText.isEmpty() ? "" : goalText + "；") + "计划操作：" + String.join("、", labels);
}

为什么要带上工具中文名：工具名是 set_layer_text 这种英文标识，嵌入模型对它没什么语义理解；中文名「改文字」能和条款里的「不得出现促销文案、水印」产生相似度。而且这个中文名来自 ToolRegistry 的 label —— 和手动接口、模型 Schema 是同一份规格，改工具名不会漏改这里。

为什么 goal 必填：只靠工具名检索会出大问题。「翻转」本身跟「背景必须纯白」没有相似度，于是背景条款召不回来，计划就被放行了 —— 但这个计划恰恰因为没做背景处理才该被拦。要查什么，取决于用户想干什么，不取决于计划里已经有什么。这是 goal 作为必填字段的理由。

判定主循环

List<Document> docs = retriever.searchForCompliance(platform, category, query);
if (docs.isEmpty()) {
    return new Result(false, query, sources, List.of(), List.of("没有检索到适用规范，需人工核对"));
}
if (rules.isEmpty()) {
    return new Result(false, query, sources, List.of(), List.of("没有配置合规规则，需人工核对"));
}

for (Document doc : docs) {
    for (ComplianceRuleProperties.Rule rule : rules) {
        if (!rule.matches(doc.getText())) continue;          // 这条条款跟这条规则无关
        boolean ok = true; String detail = "满足";
        if (rule.requireAny() != null && !rule.requireAny().isEmpty()) {
            ok = rule.requireAny().stream().anyMatch(tools::contains);
            detail = ok ? "计划包含所需工具" : "计划缺少 " + String.join(" / ", rule.requireAny());
        }
        if (rule.forbid() != null) {
            for (String forbidden : rule.forbid()) {
                if (tools.contains(forbidden)) { ok = false; detail = "计划包含禁止的工具 " + forbidden; break; }
            }
        }
        findings.add(new Finding(ref, clause(text), doc.getScore(), rule.message(), ok, detail));
        if (!ok) violations.add(ref + "：" + rule.message() + "（" + detail + "）");
    }
}

三个「不通过」的分支，都是故意的

  • 召回为空 → 不通过。没有依据就不该放行。
  • 没配规则 → 不通过。配置丢了不能静默变成「全放行」。
  • 召回了但没有规则命中 → 不通过。说明规范覆盖到了这个场景，而检查能力没跟上，应该让人看一眼。

统一的思路是 fail-closed（失败即关闭）：任何「我不确定」的情况都不放行。反过来设计（不确定就放行）会让这个校验在最该起作用的时候失效。

4.6 ComplianceController —— 独立入口

@RestController
@RequestMapping("/api/compliance")
class ComplianceController {
    record CheckRequest(@NotBlank String platform, @NotBlank String category,
                        @NotBlank @Size(max = 500) String goal,
                        @NotEmpty List<String> tools) {}

    record CheckResponse(boolean passed, String query, List<String> sources,
                         List<ComplianceChecker.Finding> findings, List<String> violations) {}
}

为什么是独立接口而不是插进 Agent 主流程：主流程已经有完整的测试和行为评测基线（44 例、跑过 3 轮）。在里面插一个会调远程嵌入接口的步骤，等于把评测的稳定性和成本都绑上去。独立接口可以先把能力做对、做出证据，再决定要不要接。这是取舍，不是遗漏 —— 面试被问「为什么没接进去」就这样答，并补一句「接的话我会放在计划校验通过之后、落库待确认之前」。

4.8 支撑件：EmbeddingConfig 与建表 SQL

@Primary @Bean
public EmbeddingModel knowledgeEmbeddingModel(
        @Value("${retouch.knowledge.embedding.api-key:}") String apiKey,
        @Value("${retouch.knowledge.embedding.base-url:}") String baseUrl,
        @Value("${retouch.knowledge.embedding.model:}") String model) {
    return new OpenAiEmbeddingModel(MetadataMode.EMBED,
            OpenAiEmbeddingOptions.builder().apiKey(apiKey).baseUrl(baseUrl).model(model).build());
}

走 OpenAI 兼容接口，所以换服务商只改配置不改代码（本机用的是阿里云百炼的 1024 维嵌入模型）。密钥、地址、模型名全部来自环境变量，仓库里一个都没有。

CREATE TABLE IF NOT EXISTS knowledge_doc (
    doc_id VARCHAR(64) PRIMARY KEY,
    version INT NOT NULL,
    title VARCHAR(200), platform VARCHAR(32), category VARCHAR(32),
    content_hash VARCHAR(64) NOT NULL,
    updated_at TIMESTAMP NOT NULL DEFAULT now()
);

只有这一张表是自己建的（Flyway V3__knowledge.sql）。vector_store 表由 Spring AI 的 initialize-schema: true 自动建，字段是 id uuid / content text / metadata json / embedding vector(1024)，HNSW 余弦索引。

pgvector 是什么。PostgreSQL 的一个插件，给它加了 vector 字段类型和向量距离运算。所以这里没有引入新的数据库 —— 还是那台 PostgreSQL，只是换了带插件的镜像 pgvector/pgvector:pg17。面试被问「为什么不用 Milvus/Qdrant」就答：语料只有 24 条，没必要多运维一个组件；现有 PG 加插件就够，真到千万级再换专用向量库。

5. 配置项全解

spring:
  ai:
    vectorstore:
      pgvector:
        index-type: HNSW            # 近似最近邻索引
        distance-type: COSINE_DISTANCE
        dimensions: 1024            # 必须和嵌入模型的输出维度一致
        initialize-schema: true     # 由 Spring AI 建 vector_store 表
        table-name: vector_store

retouch:
  knowledge:
    embedding:
      api-key:  ${EMBEDDING_API_KEY:}      # 仓库里不留密钥
      base-url: ${EMBEDDING_BASE_URL:}
      model:    ${EMBEDDING_MODEL:}
    top-k: 3                               # 规范问答
    similarity-threshold: 0.5
    compliance:
      top-k: 5                             # 合规检查
      similarity-threshold: 0.3
      rules:
        - id: background-white
          message: 背景必须纯白
          keywords: [纯白, 白底, 白色背景]
          require-any: [remove_background, replace_background]
        - id: no-text
          message: 主图不得出现文字/促销元素
          keywords: [促销, 水印, 文字]
          forbid: [set_layer_text]
        - id: square-size
          message: 首图需裁剪或补边到规定比例
          keywords: [正方形, 比例]
          require-any: [crop_canvas, prepare_delivery_sizes, expand_canvas]
配置含义调大 / 调小会怎样
dimensions: 1024向量维度和模型输出不一致，写入向量库直接报错。换嵌入模型必须同步改这里
index-type: HNSW近似最近邻索引24 条数据其实用不上索引；语料大了才有意义。是近似检索，不保证绝对精确
top-k最多召回几条调大：更不容易漏检，但无关条款混进来可能误触发规则。调小：快，但漏检风险上升
similarity-threshold相似度下限调高：无关问题被挡住，但相关条款也可能被挡。调低：召回变多，噪声变多
require-any计划必须含其中之一管「缺了什么」，比如没去背景
forbid计划不得包含管「多做了什么」，比如加了文字

7. 边界与已知代价

第一条最重要，面试必问，必须自己先说出来：召回不足等于漏检。

只有被召回的条款才会参与判定。假如某次检索没把「背景」那条召回来，缺少去背景工具的计划就会被放行 —— 而且没有任何报错。这是「用检索收敛检查范围」的固有代价。

现在的缓解：① 空召回一律不放行；② 合规这档阈值放低、条数放多；③ 专门写了一个测试 onlyRecalledClausesAreChecked 把这个行为钉死，免得以后有人误以为它是全量校验。

语料再大该怎么办：加关键词兜底（BM25 / 全文检索）做 hybrid，或者把 forbid 这类「禁止项」改成全量生效、只用检索收敛 require-any 这类「必需项」。

  • 只做计划级校验：校验的是「计划里有哪些工具」，不验证执行结果。计划里有 remove_background 就算满足「白底」，但最终图片是不是真白底，这里不管。
  • 规则是关键词映射：条款换个说法就匹配不上；目前只覆盖「背景」「文字/促销」「比例」三类，角度、模特、色彩等条款召回了也没有对应规则。
  • 没有生成步骤：不是完整的检索增强生成。
  • 阈值样本少：0.5 和 0.3 都来自少量手工查询，没有标注集。要讲得硬，得准备 20~30 条带标注的查询算召回率和误召回率。
  • pgvector 侧无自动化测试：元数据过滤、阈值、入库判重只有手动运行记录；自动化测试只覆盖判定逻辑。
  • 无冲突检测：同一平台两份规范互相矛盾时，没有「列出双方来源、交人工」的分支。
  • 无生效时间过滤：规范的生效/失效时间没有参与检索，靠人工维护语料版本。
  • 首次请求慢：懒加载会在第一次 check 时做 24 条 embedding。
  • 语料是自己编的：3 份模拟规范、24 个条款，不能据此推断真实大语料的效果。

8. 面试问答

这个模块是 RAG 吗？

是向量检索，但没有生成那一步，所以我不叫它 RAG。检索结果不进提示词、不交给模型改写，而是进校验器做硬判定。准确说是「用检索给规则校验供给约束」。

为什么不把规范直接写进提示词？

三个原因。规范会越来越多，全塞进去提示词爆、每轮都花钱；模型可能视而不见，没有确定性；出了问题无法追溯是哪条规范。做成检索 + 规则后，判定是确定的、可测试的，违规时能指到具体条款编号。

检索词是怎么构造的？为什么要有 goal？

检索词 = 本轮目标 + 计划里工具的中文名。goal 必填，因为要查什么取决于用户想干什么，不取决于计划里已经有什么。比如计划只有「翻转」，如果只拿工具名去检索，背景条款根本召不回来，而这个计划恰恰因为没做背景处理才该被拦。工具中文名来自 ToolRegistry 的 label，和手动接口、模型 Schema 是同一份规格。

为什么问答和合规用两套检索参数？

因为两边犯错的代价不一样。问答答错，用户立刻看得出来，所以宁可不答，用 Top-3、阈值 0.5。合规漏检是静悄悄放过去，没人看得出来，所以宁可多召回几条再逐条判，用 Top-5、阈值 0.3。

阈值 0.5 和 0.3 是怎么定的？

实话说是少量手工查询试出来的：0.35 时「退货政策是什么」会误召回 2 条，0.5 时是 0 条，而相关问题仍然召回 3 条。样本太少，只能算演示级取值。要做扎实，得准备二三十条带标注的查询，看召回率和误召回率再定。

这个方案最大的风险是什么？

召回不足等于漏检。只有召回到的条款会参与判定，漏召回的规则不会报错、不会提示，就是悄悄放行了。所以我做了三件事：空召回一律不放行；合规这档阈值放低条数放多；写了一个测试把「只召回部分条款就只判这部分」钉死，免得以后被误当成全量校验。语料大了要加关键词兜底做 hybrid 检索。

为什么规则用关键词匹配，不用模型判断？

确定性、零成本、可审计。硬校验必须每次结果一样、能写测试、能说清为什么不通过。用模型判断的话同一个计划两次可能给不同结论。代价是关键词脆，条款换个说法就匹配不上，这点我写在文档边界里了。

为什么用 pgvector，不用 Milvus 这类专用向量库？

语料只有 24 条，没必要多运维一个组件。pgvector 是 PostgreSQL 的插件，项目本来就在用 PG，换个带插件的镜像就行，事务和备份都沿用原来那套。真到千万级向量、要高 QPS 的时候再换专用库。

怎么保证重启不重复花 embedding 的钱？

每份规范算一个内容哈希存在 knowledge_doc 表里，入库前先比对，一样就整份跳过。内容变了则先按 docId 删掉旧向量再整份写入，避免新旧版本同时存在被检索到。

为什么没接进 Agent 主流程？

主流程有 44 例冻结评测集和一整套测试，插一个会调远程嵌入接口的步骤会把评测的稳定性和成本都绑进去。我先把这个能力做成独立接口、跑出证据。真要接，我会放在计划校验通过之后、落库等用户确认之前，不通过就不进待确认队列。

如果让你继续做，下一步做什么？

按优先级：① 补一个带标注的查询集，把阈值从「试出来的」变成「测出来的」；② 加关键词兜底做 hybrid，降低漏召回；③ 把 forbid 类规则改成全量生效，只用检索收敛 require-any；④ 给 pgvector 那层补集成测试，现在只有手动运行记录。
